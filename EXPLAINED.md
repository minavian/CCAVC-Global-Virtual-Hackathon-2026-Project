# How this project works, explained by whoever wrote it

In the interviews, **every team member must be able to explain any part of the project**, including the parts a teammate or an AI tool wrote. This file makes that possible. Every part of the code has an entry here, written by whoever built it, for a teammate who has never seen it.

## Rules

- **After you write or change code, add or update its entry here in the same pull request.** This applies to people and to AI agents. AI agents do it without being asked.
- Write for a teammate who has not read the code: plain English, short sentences, no unexplained jargon.
- One entry per part. If you change a part that already has an entry, update that entry rather than adding a new one.
- Say who wrote it (a person, or which AI tool and for whom) and when.
- If something is a simplification or a guess (a simulated value, a made-up threshold), say so.

### Landing page layout and style (`index.html`, `styles.css`)
Owner: Mina Vian · 2026-11-20, updated 2026-11-21 · Issues #3, #5, #9

**What it does.** The first screen: on the left, the three everyday RFID objects (key fob, phone, contactless card) in 3D; on the right, the headline "Those are the things you use every day." and the line "and almost nobody knows how it works…". On phones the words sit on top and the objects below. Scrolling then plays the story (see its own entry).

**How it works.**
- `index.html` holds the words as real text (an `h1` and a `p`), an empty `#stage` for the 3D canvas, the story's words (`.story`) and an empty `.track` that only gives the page its scroll length. It loads four scripts: `js/lockscreen.js`, `js/models.js`, `js/story.js`, `js/landing.js`. Three.js 0.170 comes from the jsDelivr CDN through an import map; the fonts (Inter Tight, and Antonio for the phone's clock) come from Google Fonts.
- A tiny script in `<head>` adds `data-intro` to the page before anything is drawn, so the opening can start from a blank state without a flash. If the visitor prefers reduced motion, it is not added and the page simply appears finished.
- `styles.css` pins the hero and the 3D stage to the screen (`position: fixed`), like a video frame; the page underneath still scrolls normally, with a thin ink scroll bar so the visitor can see where they are (Owner: Mina Vian · 2026-11-24; it used to be hidden). It uses a two-column grid on wide screens and a stacked layout when the window is taller than wide or narrower than 760 px. The stage covers the whole page behind the words, so objects are never cut off by a column edge. A faint SVG noise texture over everything gives a printed-paper feel.

**Layout (desktop).** The words sit in the centre of the screen, and the three objects orbit around them on an ellipse (`layout.ring` in `js/landing.js`). The front object is lowest, the back one highest and smallest. Phones keep the words on top and the objects below. The "Scroll" cue sits bottom left, clear of the front object. `index.html` loads `styles.css` and `landing.js` with a version number (`?v=`), so a changed file is never served from an old cache.

**Why it is built this way.** The words are real HTML (not drawn in 3D) so they are sharp, selectable and readable by screen readers. No build step, so anyone can open the folder and serve it.

**How to check it.** Serve the folder (for example `python -m http.server`) and open it. The `.glb` models do not load from `file://`, so double-clicking `index.html` shows the words only.

**Likely questions.**
- Q: Why does the page need a server? A: Browsers block loading model files straight from disk for security; any static host works.
- Q: Why Google Fonts with `display=block`? A: The headline is measured for the animation; swapping fonts mid-animation would make it jump, so the page waits up to 3 seconds for the real font.

### Opening animation and carousel (`js/landing.js`)
Owner: Mina Vian · 2026-11-20 · Issues #3, #5

**What it does.** The opening: the headline appears full-screen with every word faint, each word pops to full strength one by one, the headline glides to its place, the three objects spin in and land on the key fob, and the subline fades in (about 8 seconds). Afterwards the visitor can drag, fling, tap or use the arrow keys to turn the objects; after 6 idle seconds the carousel drifts back to the key fob.

**How it works.**
- **A smooth start** (`begin`, `warm`, `openingDone`). The opening waits until its 3D is ready as well as its font (at most 3 s), and the 3D is drawn once, out of sight, while it warms up (Chrome on Windows only finishes a shader the first time it is really drawn). So the heavy loading happens before anything moves: a first visit used to stutter for up to half a second at a time while the words were popping. When the opening ends, `openingDone` sets `window.__openingDone` and sends `rfid:opening-done`; the taps, the card intro and presenter mode wait for it before they load their own 3D. A full first visit, timed frame by frame, now has no slow frame from the first word to the end of the opening.
- **One playhead.** `TIMELINE` at the top lists every timing. `applyIntro(t)` sets every element's style as a pure function of the time `t`, so any moment can be recreated exactly (add `?t=4.2` to the URL to freeze the opening at 4.2 s).
- **A short scroll** (`PACE` in `timeline.js`, Owner: Mina Vian · 2026-11-24). Every scroll position in `scrollFrames` is multiplied by `PACE` (0.3), so the whole intro is 2.8 screens of scrolling instead of 9.27. At full length, every animation needed a page or two of scrolling whenever the page moved without the auto scroll below. The table keeps its first numbers, so they still read as the screens each beat was designed in; the auto scroll's stops (`INTRO`) and presenter mode's holds (`INTRO_HOLDS`) are scaled the same way.
- **Word pops** use `pop()`, a damped spring (it overshoots about 3% and settles).
- **The glide** lays the headline out at its large size and scales it down to its final place (`placeHeadline`), so the text is never blurry. A hidden copy (`slot`) holds the final position so nothing reflows when it lands.
- **The carousel** is a small physics model: a position `phase` (0 = key fob in front, 1 = phone, 2 = card) and a `velocity`. Each object's screen position comes from its angle on a tilted circle (`computePoses`): the front object is large and sharp; the other two sit behind it, bottom-left and top-right.
- **Moves** use a Hermite curve (`travel`, `advanceFlight`) that starts at the current position *and speed*, so a new input never makes anything jump.
- **Interrupting the opening** (`finishIntro(true)`): any click, key, wheel or touch freezes every element where it is and blends it to its final state. The headline's blend starts at the speed it was already moving (its easing curve is computed from that speed), and the spinning carousel lands on the key fob from its current speed.
- **Dragging** follows the diagonal between the back objects; releasing with speed flings it on (`release`). The left and right arrow keys turn it (up and down are left for scrolling). Once the story starts playing, the carousel stops taking input.

**Why it is built this way.** A single playhead makes the opening easy to tune and to interrupt cleanly; a physics carousel feels natural and never snaps.

**How to check it.** Open the page and click at any point in the opening: nothing jumps. `?t=<seconds>` freezes the opening for screenshots. `?debug` exposes `window.__hero` with `state`, `skip()`, `bring(i)` and `bench(frames)`.

**Likely questions.**
- Q: What happens with "reduce motion" turned on? A: No opening; objects swap with a quick fade instead of orbiting (`calm`).
- Q: Why does the carousel return to the key fob? A: The fob is the object the story starts with.

### 3D rendering pipeline (`js/landing.js`, `createScene`)
Owner: Mina Vian · 2026-11-20 · Issues #3, #5

**What it does.** Draws the three objects with soft studio lighting; the ones behind are blurred, grey and faded like a camera's shallow focus, and a soft motion trail follows the fast spin.

**How it works.**
1. The objects are drawn with Three.js into an off-screen image with depth (`target`, 4× antialiasing, 2× on dense screens, high-precision colour). The camera is orthographic and measured in screen pixels, so a pose of "400 px tall" really is 400 px.
2. A full-screen shader (`composite`) then reads that image and its depth: pixels far back are blurred with 24 samples in three rings, turned grey and mixed toward the paper colour. It also does the colour conversion by hand (ACES tone mapping and sRGB, exposure 0.82). During the fast spin it blends in the previous frame for the trail.
3. Lighting: a soft "room" environment for reflections, a sky/ground light and two directional lights.
4. Each frame, every object's pose (position, size, depth and rotation) comes from `computePoses`; `draw` just applies it. The story uses three hooks: `open(i, e, push)` opens a model, `fit(i, rect, …)` works out where it must stand and how big it must be to fill a rectangle (optionally only some of its parts), and `points(i, names)` reports where named parts are on screen, for the labels.

**Performance work** (the phone used to lag):
- On the first screen the canvas covers only the area the objects can reach, not the whole page (during the story it covers the screen, because the objects travel across it).
- Resolution adapts (`tune`): it drops in steps while frames are slow and rises again when they are fast.
- All shaders compile and textures upload while the page loads (`warm`), so nothing stalls mid-animation.
- Empty paper is skipped in the shader with four quick samples.
- While the taps or the card intro fill the whole screen, the landing page can't be seen, so its frame loop sleeps (`covered` in `frame`). Scrolling wakes it. This leaves the machine to the section on top.

**Why it is built this way.** The blur-and-grey look is what the sketches showed for the objects behind; doing it in one shader pass is far cheaper than blurring each object.

**How to check it.** With `?debug`, run `__hero.bench(60)` in the console: it prints milliseconds per frame, draw calls and triangles.

**Likely questions.**
- Q: Why not just use Three.js's built-in tone mapping? A: The image is processed after rendering (blur, grey, trail), so the conversion has to happen in that same final step.

### The three 3D objects (`js/models.js`, `models/`)
Models by nduchuy348-art (`models/*.glb`, branch `create-new-model`); loading code owner: Mina Vian · 2026-11-20, updated 2026-11-21 · Issues #5, #9

**What it does.** Loads the key fob, phone and contactless card, and gives each a small behaviour: the fob's lock button presses and its light glows; the phone turns around and its screen wakes; the card flips. Each model can also be opened up to show its insides.

**How it works.**
- `load()` loads each `.glb` file with `GLTFLoader`, centres it and measures its size so it can be scaled to a pixel size.
- **Sealed parts stay hidden** (`SEALED`): the models include internals for exploded views (the phone's battery and circuit board, the fob's chip and coil, the card's antenna). They can't be seen while the object is closed, so they are hidden, which halves the drawing work.
- **Opening** (`opener`, returned as `open(e, push)`): every model carries an animation called "Explode" that moves its parts apart. Instead of playing it, `open(e)` reads its keyframes at e (0 = closed, 1 = fully open), so scrolling forwards or backwards poses it exactly. The sealed parts appear as soon as it starts to open, except the fob's see-through resin potting (`STAY_HIDDEN`): it writes no depth, so the background blur would smear it into a grey square. `push` (0 to 1) then sends the outer shells further away (`PUSH`: the fob's front shell lifts up, its rear shell drops down), so the inside is left on its own.
- **Flicker fix** (`liftDecals`): flat printed layers (the card's artwork, its chip contacts) sit at exactly the same depth as the plastic underneath, which made the GPU flicker between them. Those flat sheets are nudged toward the camera in depth only.
- **Phone back** (`refineBack`, `deepenCover`): the faint brushed swirl and logo in the back's texture are strengthened (fine detail amplified, broad shading kept). The flash gets a drawn frosted lens with two LEDs (`flashFace`).
- **The H** (`redrawH`): the H on the camera island is replaced with an outline traced from a photo of the real phone (`H_PHOTO`). The island's printed layer shows its texture upside down, so the H is drawn flipped.
- **One call sets the whole look** (`looker`, returned as `look(state)`): how open it is, how much it is turned to glass, how much the coil and chip glow, whether the chip is lit (awake), the key's battery (in, being dragged, or out) and whether the key's buttons are lit. In glass, every part except the RFID parts (`RFID_PARTS`: each object's coil and chip) fades to 14% opacity but still writes depth, because the depth-of-field pass would otherwise blur it as if it were far away. Only what changed is touched, so calling it every frame costs nothing.
- **Added parts.** The fob gets a coin battery (`addCoinBattery`, 18 mm, with its + face drawn on a canvas), because a real key has one and scene 3 pulls it out. The phone gets a small NFC chip (`addNfcChip`) beside its antenna's feed, so the "Chip" label points at a real object. The lab adds a reader pad (`readerPad`: a metal puck with a three-turn copper coil under smoked glass, looking like no particular brand) and a half see-through metal plate (`metalPlate`).

**Why it is built this way.** The teammate's models are kept untouched on disk; every change happens when they load, so a newer model can be dropped in.

**How to check it.** Open the page, bring each object to the front with the arrow keys, and press Enter to trigger its action.

**Likely questions.**
- Q: Why read the animation's keyframes instead of playing it? A: The story is scrubbed by scrolling, backwards as well as forwards. Reading the keyframes at an exact point gives the same pose every time, at any speed.

### The phone's lock screen (`js/lockscreen.js`)
Owner: Mina Vian · 2026-11-20 · Issue #5

**What it does.** The phone has an always-on display (a dim clock on black). When it comes to the front it turns around and wakes into a lock screen: a blue-grey wallpaper, a tall live clock, the date, four widget tiles and two shortcut buttons, which arrive one after another.

**How it works.** Each element is its own flat layer on top of the phone's glass, with a picture painted once: the wallpaper, an "atlas" of icons, the clock (repainted once a minute) and the date (repainted once a day). The animation only changes each layer's opacity, position and size (`update`), so nothing is redrawn while it moves. Layers are stacked a hair apart and drawn in a fixed order so they never fight.

**Why it is built this way.** The first version redrew one large picture every frame and sent it to the graphics card, which took about 37 ms per frame and made the phone stutter. Layers bring that to the same cost as a still frame.

**How to check it.** Bring the phone to the front: it turns and wakes. The clock shows your real time.

**Likely questions.**
- Q: Is the lock screen copied from a real phone? A: It is drawn in code and modelled on a ColorOS lock screen; no personal details are shown.

### Every day: three taps (`js/taps.js`, `models/subway-card.glb`)

Owner: Mina Vian · 2026-11-22. Metro ticket model by Akris Luno (`nduchuy348-art`, branch `create-new-model`).

**What it does.** The section right under the landing page. Three small 3D scenes play one after another: a metro ticket taps a ticket gate and the gate opens; a bank card taps a payment terminal and the payment is approved; a car key's unlock button is pressed and the car opens. Each has one short line under it: "Tap. The gate opens.", "Tap. The payment goes through.", "Click. The car opens."

**How it works.**
- **Loading after the landing's opening** (`afterOpening` in `taps.js`). The taps load their 3D once the landing's opening is over (`rfid:opening-done`), or as soon as the visitor scrolls: loading during the opening made it stutter. Until then, the words show and the 3D fades in when ready.
- **No stall as it scrolls in** (`load` in `taps.js`). Once the models are in, every part of every scene is drawn once, out of sight, from each panel's own view, with the parts that wait hidden shown for that one draw, then cleared. Chrome on Windows draws through Direct3D, which only finishes a shader the first time it is really used: without this draw the first frame of the taps on screen took about 160 ms, a visible hitch as the page scrolled in.
- **Where it sits.** The landing page is pinned to the screen, so the section starts one screen down. It has a paper background and slides up over the landing page like a sheet. It is at least one screen tall, so it covers the landing page fully. The card intro ([What RFID is](#what-rfid-is-the-card-intro-jsintro)) comes next. After it, the landing page shows again and the story starts from its first frame: `landing.js` counts the story's scroll from the top of `.track`, which comes right after the intro.
- **One canvas, three cameras.** `index.html` has a `.taps-row` with three `.tap-view` boxes and one `<canvas>` under them. `js/taps.js` keeps the three scenes in one Three.js scene, 60 m apart, and gives each its own camera. Every frame, it measures each box and draws that scene into it with a scissor box (`draw`). One WebGL context serves all three.
- **Pure functions of time.** Each scene has `apply(t, r)`. `t` is the panel's time (0 to `PLAY`, 3.4 s) and `r` is the reset (0 to 1). The pose is computed from these two numbers alone, so the loop can stop, restart or jump at any point. The timings are in the `PLAY`, `HOLD`, `RESET` and `ARRIVE`/`LEAVE` constants at the top.
- **The order.** On wide screens one clock (`cycle`) plays the gate, then the payment, then the car. All three hold their finished state, reset together, and the loop starts again. On phones the panels are stacked, so each one plays its own loop while at least half of it is on screen (`own`, `shown`). The thin bar under each line fills while its panel plays.
- **The card's flight** (`glider`). The card floats with a slow bob, follows a curve to the reader and lands straight down onto it. It presses once and floats back. The flight eases in and out (`inOut`), and the turn finishes before it lands.
- **The gate** (`gateSet`). It has two rounded cabinets and a dark reader pad. Two glass flaps turn on hinges at the cabinets. Copper rings spread from the pad while the ticket is read (`ripples`: the reader's field, the same copper as the rest of the site). Then the lights turn green, a tick appears on the front display, and the flaps swing open toward the exit.
- **The terminal** (`terminalSet`). The screen is a canvas texture, redrawn only when it changes (`drawScreen`). Four status lights come on one after another while the card is read, like on real card terminals. "Approved" appears as the card leaves.
- **The car** (`carSet`). The body is one side outline extruded across the car with rounded edges. The windscreen and rear window follow the outline's curves (`ribbon`). The near front door is a separate panel on a hinge, with a dark opening behind it that lights up warm. The key is the team's fob model, shown large. Its unlock button moves in by 0.9 mm, rings travel toward the car, the light bar blinks amber twice, and the door swings open.
- **Models** (`loadModel`). The ticket, the bank card and the key are the team's GLB files, loaded and centred here. Parts sealed inside them (coils, chips) can never be seen, so they are not drawn. Flat printed layers get the same depth nudge as in `models.js` (`liftDecals`), so they don't flicker. The gate, terminal and car are built in code from simple shapes. The ticket is drawn 3.6 times its real size so it can be seen next to a full-size gate. The key is drawn 19 times its real size. The terminal and bank card are at true size.
- **Only when needed.** The models load when the section is about one screen away. Frames are drawn only while the section is on screen, the tab is visible and the loop isn't paused.

**Why it is built this way.**
- One shared canvas instead of three: one WebGL context, one set of lights, one frame loop.
- The gate, terminal and car are made from simple shapes rather than detailed models. They are the backdrop: the real models (ticket, card, key) stay the focus. They also stay neutral and look like no real brand.
- The section slides over the pinned landing page rather than pushing it away, because the landing page and the story share one pinned stage. Counting the story from `.track` keeps the film exactly as it was, only later on the page.

**What is simplified.** This section is a picture, not the simulation. Nothing here is computed from RFID physics; the copper rings only show that the reader's field is there. The key's button is powered by the key's own battery, as scene 3 of the story says. The amount on the terminal is made up.

**How to check it.** Serve the folder, scroll one screen down from the landing page, and watch the three scenes play in turn. Press **Pause**: everything stops where it is. With reduced motion turned on in the system, all three show their finished state and nothing moves. Keep scrolling: the card intro plays, then the landing page comes back and the story starts. Add `?debug` to the address and run `__taps.seek(4.5)` in the console to freeze the loop at 4.5 s.

**Likely questions.**
- Q: Why are the ticket and key bigger than life? A: At true size, a ticket next to a 1 m gate, or a key next to a car, would be a few pixels. The scenes are illustrations, so the hero object is scaled up and the backdrop stays at true size.
- Q: What happens on a phone? A: The panels stack, and each plays its own loop while it is on screen, so nobody misses one that played off screen.
- Q: Does it slow the page down? A: All three scenes together took about 3 ms per frame on our test machine. Nothing is drawn while the section is off screen.

### What RFID is: the card intro (`js/intro/`)

Original section written by OpenAI Codex for the project team · 2026-11-22 (the team's `ui-rebuild` part 2, in `Teams parts/`). Moved into this page: Owner: Mina Vian · 2026-11-22. The reader slab and the gliding drag were rebuilt · 2026-11-23.

**What it does.** The section after the three taps. One bank card, played by scrolling: it opens like a mouth and lets out the letters R, F, I, D. The letters spell "Radio-Frequency Identification", then one line says what it does: "This technology works by exchanging data using radio waves. That's literally it." An X-ray shows the antenna and the chip, and the card asks how it can work with no battery. At the end you drag the card onto a reader.

**How it works.**
- **Where it sits.** `index.html` has a tall `<section class="intro">` right after the taps. Inside it, `.intro-stage` is `position: sticky`, so it stays on screen while the section scrolls past. Its paper background covers the pinned landing page, like the taps.
- **Coming in from the taps.** While the stage is still sliding up, before it pins, the playhead runs from `ARRIVE` (-1) to 0, one screen of scroll. The first row of `cardFrames` places the card higher in the stage and turned away. So the card rises more slowly than the page and turns to face you as the stage settles. The taps and the intro use the same paper colour, so there is no seam between them.
- **Leaving for the story.** The section has the same soft paper edge as the taps (a wide `box-shadow`). As it slides away, the landing page fades in under that edge, and the story starts from `.track`.
- **One playhead.** `js/intro/timeline.js` turns the scroll into one number, the playhead (`scrollTime`). Repeated values in `scrollFrames` hold the picture still for a stretch of scroll, so there is time to read. Everything else is a function of the playhead: the card's pose (`cardPose`), when each line fades in and out (`beats`), and when the X-ray shows.
- **One scroll, one animation, from the top to the card's drop** (`autoplay.js`, Owner: Mina Vian · 2026-11-24). The visitor's scroll is in charge: scrolling down, every scroll plays exactly one animation; scrolling up is the browser's own. The stops are:
  1. the landing (the top of the page);
  2. the everyday taps, framed (on a phone, where the panels stack taller than the screen, one stop per screen);
  3. the card, slid in over the taps and facing you;
  4. "RFID", as the card opens and the letters fly out;
  5. "Radio-Frequency Identification";
  6. the one-line definition;
  7. the X-ray: antenna, chip, "So how does it talk?";
  8. "Here's how: drag the card to the reader", the last stop.

  - **No wait.** A scroll, however small, starts the page moving on the next frame, and the animation with it. Each stop is a stretch where the picture holds still (a reading hold in `scrollFrames`). Leaving a stop, the page jumps over the rest of that stretch at once, because nothing on screen changes there, and the glide covers only the part where things move. A still stretch inside an animation (`STILL`: the card's mouth closed, before the letters spell the name) is jumped the same way, so no animation pauses half-way. The glide starts at full speed and slows softly into the stop (`ease`, a quarter sine). An earlier version stopped in the middle of each hold and glided 3 s through it, so after a scroll nothing moved for 0.3 to 1.1 s, and the last second of every glide was still too.
  - **No overscroll.** However hard or fast the scroll, it plays the next animation only, for that animation's own time (the third number in `INTRO`: 1.8 to 2.6 s, and 3.5 s for the last one, where the card moves beside the reader; a stretch of plain page, the landing to the taps, takes 1.56 s a screen), then stops. These are 1.3 times the first timings (the last one 2.5 times), which felt too fast. Entered part-way, an animation plays the rest at the same pace.
  - **How a scroll is counted.** A new scroll starts once the wheel has been still for 300 ms (`BURST`), or when it turns the other way, or when it is pushed again much harder (more than three times the last event, after the scroll has lasted 300 ms): a new swipe while a trackpad still coasts from the last one. The coasting events after a swipe only get smaller, so they never count again. A swipe on a touch screen counts once its finger has moved 12 px up. Arrow Down, Page Down and space count too; a held key's repeats don't, so holding a key never races through several animations.
  - **A scroll mid-glide.** Down, the animation playing finishes at once and the next one starts. Up, the glide stops where it is and the page scrolls up as usual.
  - **Scrolling up is free** (2026-11-24). The wheel, a trackpad, a swipe and the up keys move the page up as on any other page, as far and as fast as the visitor scrolls, and the animations play backwards with the scroll. Scrolling up used to go back one animation per scroll, over 2 s, and swallowed the rest of the scroll meanwhile: however much the visitor turned the wheel, the page went back one step at a time, and it felt as if it couldn't scroll up. A scroll down after scrolling up starts from wherever the page is and plays on to the next stop.
  - **How it moves.** It moves the real page scroll (`scrollTo`), so everything on the page follows exactly as if the visitor had scrolled. It is timed by the real clock, so slow frames don't stretch it. The stops are read from the page each time (`stops`).
  - **Catching the scroll.** To go to the next animation instead of scrolling, a scroll has to be caught before the page moves, with listeners that may cancel it. They are on from the top to the end of the last stop (`arm`, `inside`). Below it the page scrolls as usual: a scroll down at the last stop leaves for the rest of the page. If the page moves some other way (the scroll bar, a link), the glide lets it.
  - It is off with reduced motion, and while presenter mode runs (`window.__presenting`).
  - **A page with no height yet** (a hidden tab) gets one stop for the taps; the stops are read again once it has a size. A step of 0.9 × 0 px used to make the taps' loop add stops forever, until the browser gave up with an error, freezing the page for seconds (found in the browser's console, 2026-11-25).
- **Counting from the section.** The original was a page of its own. Here, `main.js` measures where the section starts (`startY`) and counts the scroll from there.
- **The card** (`card-scene.js`). It loads the team's `models/contactless-card.glb`. The X-ray fades the outer layers and turns the copper antenna brass.
- **The mouth bends like a sheet** (`bendSheet`). The two front layers stay glued along the right edge and lift as one sheet: a soft crease near the edge (`HINGE`, 0.17 radians) and a curl that grows toward the free edge (`CURL`, 0.40 more). The model's flat layers only have vertices round their outline, so `sliceAlongX` first cuts them into 72 strips across the card. A vertex shader then walks along the sheet from the glued edge, adding up its direction with Simpson's rule. So every point keeps its distance along the card: the sheet bends but never stretches. Each normal turns by the same angle, so the light slides along the curve. `sheetPoint` does the same sum in JavaScript, and `mouth()` uses it to find the middle of the gap.
- **The opening** (`timeline.js`, `mouthAt`, `curlAt`). One smooth open and one smooth close, made from smootherstep curves, which start and stop with no kick. The curl runs a moment behind the crease, the way a sheet bends before it lifts and straightens after it lands.
- **Smooth motion everywhere** (`easing.js`).
  - The card's pose, and the scroll-to-playhead table, go through a monotone cubic curve (`monotone`). The card glides through each keyframe instead of stopping on it, and never overshoots.
  - The playhead, the drag, the lift and the mouse tilt each follow their target through a critically damped spring (`spring`, `follow`). A scroll that starts or stops suddenly still starts and stops the card softly, because the speed carries over from frame to frame.
  - **The drag glides.** While you hold the card, it follows the pointer through a softer spring (`GLIDE` in `main.js`), so it trails about a fifth of a second behind a moving pointer and catches up smoothly instead of sticking to it. The spring's speed also tips the card the way it is moving (`LEAN`), like a card held at one corner. Let go away from the reader and it glides home.
  - The arrival from the taps eases out exactly where the scroll curve eases in, so the two join with no bump.
- **The letters** (`main.js`, `paintLetters`). Four real HTML letters fly out of the gap in the card's mouth, then spell the full name in three lines: **R**adio-, **F**requency, **ID**entification. I and D share the last line (`STACK_ROW`), and D moves one I-width to the right. On phones, the line under the name sits right below those three lines (`meaningY` in `timeline.js`). Each flight (`settle`) leaves from rest, overshoots by about 4% and lands with no speed left. The rise is a sine squared, so it lifts off and touches down level.
- **The big type.** The letters R, F, I, D use the site's Inter Tight, a variable font: its weight can be any number, not just a few fixed steps. `index.html` loads the full range (100 to 900). Each letter leaves the card at the thinnest weight (100) and fills out to 800, like the taps' title (`THIN`, `FULL` and `weights` in `main.js`, `paintLetters`). The weight follows the distance the letter has travelled, not the clock. So it starts thickening the moment the letter leaves the mouth and is full as it arrives, all while it moves. It thins again if you scroll back. `measure` takes the letters' widths at full weight, so the layout is right even mid-flight.
- **No title screen in the middle.** A full-screen "How It *Works*" title used to sit between the one-line definition and the X-ray. It was taken out on 2026-11-24 because it said nothing (Owner: Mina Vian). Its hold left `scrollFrames`, so the section is 0.67 screens shorter (9.27 screens, before `PACE`). Its two card poses left `cardFrames`, so the card glides straight from beside the definition to the X-ray. Its font, Instrument Serif, is no longer loaded.
- **The lines** (`signals.js`). One 2D canvas draws the spray from the mouth, the radio wave, the label lines and the reader's rings. The rings step aside once the close-up shows the reader's real field in 3D.
- **The reader** (`reader-model.js`). One rounded slab, like a modern payment pad: a satin graphite body whose outline is a superellipse (a "squircle", `squircle`), so its corners curve into the sides with no visible join. Its edge is rounded all the way round (`slab`: the outline extruded with a round bevel, then its vertices merged so the edge shades as one smooth curve). On top: a flush black glass panel, the contactless mark and a slim light bar. The picture `images/intro/reader.webp`, shown when WebGL is off, is a render of this same model from the same angle. Bringing the card near opens the close-up ([The close-up](#the-close-up-how-a-tap-works-jsintrocinemajs)); you can also press the card with the keyboard.
- **Only when needed.** The 3D card loads when the section is about one and a half screens away. Frames are drawn only while the stage is on screen.

**Why it is built this way.** The pinned stage keeps one card on screen through the whole idea, so nobody loses track of it. Real HTML text stays sharp and screen readers can read it. Every CSS rule starts with `.intro`, and the two class names the page already used are renamed (`.intro-stage`, `.intro-callouts`), so this section cannot change the landing page or the story. The reader's sizes live in `reader-size.js`, which needs nothing else, so the scroll, the drag and the close-up's words still work if three.js fails to load; only the 3D is missing then.

The first version eased each keyframe in and out separately (smoothstep), and followed the scroll with a one-step lag. So the card stopped for an instant at every keyframe, and its speed jumped whenever the scroll started. The opening was a stiff flap on a hinge, with a curl that had no vertices to bend. The changes above fix those three things. A scripted wheel scroll through the opening, measured at 60 frames a second, showed peak acceleration 3 times lower and peak jerk (the sudden kick) 4.3 times lower.

**What is simplified.** "Card detected" is a check that the card was dropped close to the reader, not a radio link.

**How to check it.** Serve the folder, open it, and scroll down once, a little: the page should move at once to the everyday taps and stop. Each further scroll, small or hard, plays one animation and stops: the card slides in, the card opens and the letters fly out, then the name, the definition, the X-ray, then "Here's how". Nothing should stand still after a scroll, and a hard scroll should never skip an animation. A couple of seconds after "Here's how" the card is carried to the reader and the close-up plays. A scroll mid-glide moves on to the next animation at once. Scrolling up moves the page up freely, with the animations playing backwards. To try it by hand, drag the card onto the reader yourself. Press Tab first on the section to find **Skip to the card and reader**.

**Likely questions.**
- Q: Why is the playhead not just the scroll position? A: Some parts need more scroll than others. The table in `scrollFrames` gives each beat its own length, and holds.
- Q: Isn't taking over the scroll annoying? A: It never makes the visitor wait: every scroll moves the page at once, one animation per scroll, and it only covers the way to the card's drop. Two earlier versions felt locked. The first waited for the scroll to settle and glided at its own pace. The second let the browser scroll freely, so a hard scroll still had to cover twelve screens. Without it, a visitor had to scroll about twelve screens to reach the card's drop.
- Q: What if WebGL is off? A: Two pictures of the same card (`images/intro/credit-card-*.webp`) stand in for the 3D card.
- Q: Why does the card trail the scroll a little? A: That is the spring. It is what makes a sudden scroll look smooth. It catches up within about a third of a second.
- Q: Is the bend physically right? A: It is a sheet that bends without stretching, with the bend we chose. Real card layers are glued all over and don't open at all. The mouth is a picture, not a teardown.

### The close-up: how a tap works (`js/intro/cinema.js`, `effects.js`, `card-scene.js`, `reader-model.js`, `lab-model.js`)

Owner: Mina Vian · 2026-11-23. Rebuilt as an interactive close-up · 2026-11-23, updated 2026-11-23 (the conversation and the river of light; then the river's route made chip, coil, coil, chip; then the readout moved to the bottom middle, like a subtitle; then the message's label held still; then the conversation rebuilt on the real physics: the reader's field, its gaps, and the card's load; then the readout made small, with no box; then the river of light brought back, carrying the real signals along real field lines, with radio waves; then the whole of each coil made to send and receive; then rebuilt as clear stages: current round every turn of a coil, radio waves across, the chip at work; then, on 2026-11-24, put back on the real physics, on one clock, with the power's flow as the moving light; then smoothed the way a card's demodulator sees the signal, so it pulses instead of blinking; then the field and the copper given their direction; then four steps on how the field powers the card, labels on the parts, and autoplay; then made simple: one picture language, one new thing per step, the card held 3 cm up, and one camera angle; then a lab after the tap, where the visitor changes everything and watches it respond).

**What it does.** It shows what happens in a tap. **It plays by itself** until the visitor does anything: once the card is ready it is carried to the reader, each step holds for a few seconds (a ring round the right arrow fills until the next one), and Ask is pressed for them, so a presenter can just let it run (about 45 seconds). The moment the visitor touches, clicks, drags or presses a key, it stops and they drive it; the **Pause / Play** button at the top right, or the space bar, starts it again. The lights go down after the drop, so the field and the current glow.

**One picture language.** Only two kinds of thing move, and each always means the same:
- **Beads of light running along a wire are electricity.** Golden while power comes in; blue while the card answers. They run round one loop on each coil, its outer turn, and on the card from its coil into the chip. In the dark the copper itself goes darker, so the light stands out from the copper's own colour.
- **Rings travelling between the coils are the magnetic field.** Orange rings rise from the reader's coil and land on the card's coil, taking its shape as they go. Blue rings come back down from the card to the reader: the answer.

The card is held 3 cm over the reader (a realistic tap), so the two coils are clearly apart, and every step until the check uses the same camera angle, from the front and a little above, so nothing jumps.
1. **Bring the card near.** As you drag the card toward the reader, the close-up comes in and follows the card's distance. The camera pushes in on the reader, and the reader turns see-through to show its copper coil, with the current running round it and its field rising. The card turns see-through too, a current starts to run round its coil, and close enough, the current runs into the chip and it lights up. Pull the card back and it all runs backwards.
2. **Drop it.** The card settles onto the reader, and the tap plays from step 1 (or you step through it with the arrows on either side of the readout, **›** and **‹**, the arrow keys, or the dots under it, which jump to any step). Each step lights only the part it is about, names it on screen with a thin line to it, and dims the rest:
   1. **Electricity runs round the reader's coil.** Only the reader's coil lights up, with beads of light running round it. The card is dim. Label: `Reader's coil`.
   2. **That makes a magnetic field.** Orange rings rise from the reader's coil up to the card. Label: `Magnetic field`.
   3. **The field makes electricity in the card's coil.** Beads of light start running round the card's coil, and the rings dim so it stands out. Label: `Card's coil`.
   4. **That electricity powers the chip.** The light runs round the chip's own small loop and into it, the chip glows, and the chip-power meter fills from 0% to 100%. The camera moves in so the whole card fills the picture, a little more from above, with the chip on the left, and the reader fades almost away. Label: `Chip`.
   5. **Your turn.** **The right arrow becomes Ask.** Press it and the reader asks "Who are you?" the way a real reader does: it switches its field off for short moments. The orange rings and both coils' light dim in each of those moments, in a soft rhythm, and the card's chip flashes each time it has read a byte. When the question is over, the card's chip pulses while it works out its answer, for the standard's real wait, and the `Chip` label points to it. The camera stays still: the wait is only about a second.
   6. **The card answers with its ID.** It switches a load on its coil on and off: the card's coil turns blue, its light runs the other way, out of the chip, and blue rings come down to the reader, swelling each time the switch closes. The reader's coil dips a little each time and turns blue as it takes the answer in, and the reader's chip flashes as it reads each byte. The answer is the card's ID, `04 7B 21 9E`.
   7. **The reader checks the ID.** The lights come up and the camera pulls back. The ID is shown next to the reader's chip.
   8. **Verified:** the card lands on the reader, and the check mark.
   9. **Try it yourself** (the lab). The lights go down again and a panel opens beside the close-up. The visitor changes the tap and everything responds at once, worked out live by the site's physics engine:
      - **Distance** (0.5 to 10 cm): the card rises or falls over the reader, the camera pulls back to keep both in view, and the rings fade as they climb, as the real field does with height.
      - **The card's angle** (0 to 90°): the card tips over; less field passes through its coil.
      - **Metal behind the card** (none, or 2 cm, 1 cm, 5 mm or 2 mm behind): a steel plate appears behind the card, labelled `Metal`, and soaks up the rings near it.
      - **The reader's power** (0 to 150%): the reader's current and its rings brighten or dim.
      - **What the card is tuned to** (5 to 30 MHz; real cards are tuned to 13.56): the card collects less when it is tuned away.
      - **The card's ID** (four bytes in hex): its check byte is worked out as it is typed, and its answer carries the new ID. An ID that can't be a card's says why under the field (`idProblem` in `lab-model.js`; Owner: Mina Vian · 2026-11-25): one starting with 88 at once ("88 can't come first: it means a longer ID follows.": 88 is the cascade tag, which tells the reader a 7- or 10-byte ID follows, so no 4-byte ID can start with it), and one that isn't four bytes only once the field is left, so a half-typed ID isn't scolded. The note is a live region, so a screen reader hears it, and the field points to it (`aria-describedby`).
      - **Ask the card**: the question goes out as in step 5. If the chip is awake, it answers with its ID; if not, nothing comes back and the readout says "No answer. The chip has no power."
      - **Situations to try**, one click each: Normal tap, Too far, Side-on, On metal, Weak reader, Badly tuned. **Reset** puts everything back.
      Live readings show the field at the card (A/m, with a mark at the standard's minimum, 1.5 A/m), the voltage at the chip (with a mark at the 2 V it needs to wake), how far it works with everything as set, and the answer's strength (how much the reader's own current changes when the card answers). A chart shows the voltage at the chip against distance, or against the reader's frequency, with a dot where the setting is now and a dashed line where the chip wakes. The readout says, in one sentence, whether the chip is awake and why. Played by itself, the lab shows its controls at work for 20 seconds: the card is moved away until the chip sleeps and back, turned side-on and back, then a metal plate is slid behind it and away.

   Then the explanation, with **Watch again** (which plays it by itself again) and **Try again**. At any point after the drop you can **drag the stage to turn the camera** (sideways only on a phone, so the page still scrolls). Escape takes the card off.

**How it works.**
- **The readout** (`index.html` `.readout`, `paintFilm` in `main.js`). One small readout along the bottom, in the middle, like a film subtitle, is the only text on screen during the close-up. It has no box: only its words, numbers and buttons over the background, with a soft halo in the background's colour (dark in the conversation) so the words stay clear where they cross the 3D. The instructions fade out before it fades in, and the explanation only appears once it has gone, so there are never two texts to read at once. From the top down it shows:
  - one sentence at a time, in bold;
  - under it, one line of small print with a little more (`detail` in `STEPS`, `APPROACH_DETAIL` while dragging), for example "The card has a copper coil too, round its edge." Both are one polite live region for screen readers, so they are read together;
  - three small meters;
  - after the drop, a dot for each step, with the current one long.
  The meters are:
  - the radio frequency, 13.56 MHz, with a little running wave;
  - while dragging, the distance in centimetres; after the drop, when each step happens in a real tap, with a 0 to 5 ms bar;
  - the chip's power: while dragging, the share of the field the card collects; after the drop, 0% until the current reaches the chip in step 3 (`charge`), then 100%.
  After the drop, round buttons sit on its sides: **‹** (Back) on the left and **›** (Next) on the right. They are grid columns of the readout (`.readout-nav` uses `display: contents`, so its buttons and dots are placed straight into the readout's grid), so the words stay in the middle. On a phone the meters and dots take the full width under the arrows, so the numbers have room. After the drop the readout's words turn light as the lights go down (`.is-dark`), and the right button becomes an orange, pulsing **Ask** (dimmed while the question is on its way). On a phone the reader rests low on the screen, so while the card is dragged the readout waits at the top, in the instructions' place, and fades in at the bottom on the drop.
- **Distance and power** (`cinema.js`). The drag is on a flat screen, so its distance from the reader's centre is turned into centimetres (`centimetres`). The edge of the drop zone is about 4 cm, inside where a real bank card wakes up, and the nearest is half a centimetre. Since 2026-11-25 (Owner: Mina Vian) the drag runs on the same physics engine as the lab (`padAt` in `cinema.js`: the card reader at full power, the card facing it), so the drag and the lab can never disagree. The chip wakes at 4.85 cm (`WAKE_CM`, from the engine's `range`), and the sentence turns to "strong enough to power the chip" at that same place. The card's current is drawn as in the lab, as bright as the power it carries and as fast as it is strong, so at 7 cm it shows almost nothing. The readout's chip power is the power the chip gets as a share of what it needs to wake, (V / 2 V)² (`chipShare`, and `chipPower` in the lab), so it reads 4% at 10 cm, 24% at 7 cm and 100% once awake. An earlier version used a rough curve of its own (`power`, kept only in case the engine fails to load), which lit the card's coil at 16% and full speed at 6 cm, woke the chip at 4 cm against the engine's 4.85, and called the voltage's share "power". The sentence changes with bands of distance and holds for 0.15 cm past each edge, so it doesn't flicker (`approachBand`).
- **Levels, not a clock.** Everything the close-up can show is a number from 0 to 1 (`IDLE` lists them): how see-through the card and the reader are, how strong each current is, the rings, the check mark, how dark the lights are (`dark`), how much the rest of the page shows. `approach(cm)` gives the levels for a distance; each of the steps in `STEPS` gives its own. `main.js` glides every shown level toward its target on a spring, so moving the card, or pressing Next or Back, never jumps. The camera (zoom, the point it looks at, its angle, its lens) glides the same way, with the zoom in even steps (a log scale), so 1× to 10× feels steady.
- **Two lenses** (`card-scene.js`). The drag and most steps use a flat lens with no perspective, like a plan drawing. Each shot also has a field of view (`fov` in `SHOTS`, in degrees). Above zero, a real perspective camera takes over, placed as far back as keeps the point in focus the same size on screen. So when the field of view widens between shots, the camera moves in while the framing holds and the depth opens up around it: a dolly zoom. The close-up's shots use a 30° lens, from the front and a little above, so the reader's coil, the gap and the card's coil stack up the screen.
- **The conversation** (`TALK` and `message` in `cinema.js`). The two messages are real ISO/IEC 14443-3 anticollision frames, built by the site's own `js/rfid/iso14443a.js` (`standardFrame`, `bcc`): the reader sends SEL `0x93` with NVB `0x20` ("everyone, send your whole ID", 18 bits); the card answers with its four ID bytes and their check byte (BCC `0xC0`), 45 bits. Each byte is 8 bits, lowest first, then an odd check bit. They go on the air exactly as ISO/IEC 14443-2 Type A sends them at 106 kbit/s, worked out by the same functions the story's simulations use:
  - **The question:** the reader switches its field off for 2.36 µs at a time (100% ASK). Where each gap falls in a bit says the bit (modified Miller coding, `millerPauses`). The field dies away and comes back in a fraction of a microsecond (`fieldAtTag` in `js/rfid/air.js`). The card's chip keeps running through each gap on the charge it has stored.
  - **The answer:** the card switches a load across its coil on and off 847,500 times a second (the subcarrier), in the first half of a bit for a 1 and the second half for a 0 (Manchester coding, `manchesterSwitch`). In the 3D the switching is shown as on while it is happening at all (the subcarrier is too fast to see even slowed down), softened over a quarter of a bit so each burst swells and fades instead of strobing.
  - **One clock.** Everything runs on the same clock, the real one slowed down about 16,000 times: one bit takes 0.15 s, so the question takes 3.15 s, each gap shows for 38 ms, and the answer takes 7.05 s. In each gap the whole stream of rings and both coils dim together, as the field does everywhere at once.
  - **The chip's wait** is the standard's real one (`answerDelay`, 86 µs after the reader's last gap), on the same clock: the answer starts 4.22 s after you press Ask (`ANSWER_AFTER`), so the card's chip is seen working for about a second. The readout says "The chip works out its answer.", the chip pulses (`blink`) and its label shows.
  - **Smooth, as a receiver sees it.** The real signal is sharp: a 2.36 µs gap is 38 ms as shown, about seven times a second, and drawing it at full depth across the whole scene made the picture strobe. A real card doesn't see it sharp either: its demodulator runs what it picks up through a smoothing filter before it decides on each bit. `demodulate` in `cinema.js` does the same, two RC stages with a time constant of 10 samples each (about a third of a bit), and the 3D follows what comes out: each gap is a soft dip (to 66%, drawn half again as deep), each burst of the card's load a soft swell. The most anything changes from one frame to the next is about 0.12 (it was 0.92), so it pulses instead of blinking. The trace under the label keeps the exact signal.
  - `message(name, seconds)` gives, at any moment, how far into the frame it is, the reader's field as the card's demodulator sees it (`amp`), the card's switch as the reader sees it (`load`), the exact signal (`exact`, for the trace), how many bits the receiving chip has read (each at the end of its bit time) and a soft `beat` each time it has read a whole byte (nine bits with the check bit). Those come straight to the 3D every frame, not through the springs.
  - The steps' real times come from the same frames: the question at 1.00 to 1.20 ms, the answer at 1.27 to 1.71 ms. While a message is on the air, the readout's real-time meter counts up in microseconds.
- **The field's rings** (`stream` in `effects.js`). A ring leaves every 0.3 s and takes 1.5 s to cross, so about five are in flight. Each is a thin band in the shape of the reader's coil with a wide, faint halo round it, brightest halfway across. Going up, a ring starts on the reader's coil and changes shape as it rises (scaled and turned with the card) until it lands exactly on the card's outer turn, 80 by 49 mm; going down, the other way round. The stream's brightness follows the signal as a receiver feels it: in the question the orange stream dims in each of the reader's gaps (to 12%); in the answer the blue stream swells each time the card closes its switch. While the card is still in the hand, the rings just spread as they rise, and on the light page they are lighter and have no halo, which looks heavy on paper. As the card docks, where they land blends from that spread to the card's coil, so nothing jumps at the drop.
- **The lab** (`lab-model.js`; `setLab`, `paintLabPanel`, `paintPlot`, `labAsk`, `labMessage` in `main.js`; the `.try` panel in `index.html`). The controls are turned into the inputs of `RFID.physics.solve` from `js/rfid/physics.js`, the engine the simulations further down the page run on: the distance between the coils, the angle between them, a metal plate behind the card (modelled as a mirror image of the reader's coil), the reader's current, and the card's tuning capacitor (a coil tuned to f has C0 × (13.56 MHz / f)²). It solves the coupled circuits in real units and returns the field through the card's coil, the voltage at the chip, whether the chip wakes, and how much the reader's current dips when the card answers; `range` finds how far the card still wakes by bisection. A solve takes about 2 µs, so the lab works out the whole setting, the reach and the chart's 121 points on every change. `labLevels` turns the answer into what the close-up shows: the card's height and tilt, the plate, the reader's current, the card's current (from the induced voltage), the chip (awake or not), the chip power meter and the answer's strength; the springs then glide everything there, as in the steps. The sentence (`status`) never guesses the reason the chip is asleep: it puts each control back to normal on its own and asks the physics whether that alone would wake the chip; the first that would is the reason (and if none would on its own, it says several things are working against it). The lab's conversation reuses the steps' (`message`, `talkLevels`): the question goes out, and the answer follows only if the chip was awake when it was asked. A new ID rebuilds the answer frame (`setCardId` in `cinema.js`) with its own check byte; every answer frame is 45 bits, so its timing never changes. The panel's class is `try`, because the scroll story's own lab already uses `lab`.
- **What the lab draws is the physics** (`labLevels` in `lab-model.js`, Owner: Mina Vian · 2026-11-24). Every moving thing in the lab's 3D comes from the solved circuit, so no setting can show something that isn't happening:
  - The reader's coil current and its field rings follow the reader's power exactly (`emit`, `field`): at 0% there is no current, no ring, Ask is greyed out (a reader that makes no field can't ask), and the readout's radio frequency reads Off with its wave lying flat. An earlier version kept 10% of the current and 15% of the rings even at 0%.
  - The current in the card's coil is the induced voltage as a share of a normal tap's (`current`: 4.2 V at 3 cm on the card reader). It is drawn as bright as the power it carries, the current squared (`receive`), and its light runs as fast as the current is strong (`cardPace`; `readerPace` does the same for the reader's coil, in `effects.js` and `card-scene.js`). Too far (7 cm) the card gets a fifth of the current, so it shows a twenty-fifth as bright, crawling at a fifth of the speed: next to nothing, as in life. An earlier version drew the induced voltage to the power 0.7, which made the same fifth look a third as bright and run at full speed, so the card seemed to have electricity when it had almost none.
  - **A negligible current shows nothing** (`shownPower` in `easing.js`). Measuring the rendered pixels showed that even at a twenty-fifth of a normal tap's brightness, the card's coil still showed faint moving specks on the dark close-up: too far, the card still seemed to carry a little electricity. So below about a twentieth of a normal tap's power the card's light is not drawn at all, and it fades in to full by a fifth: such a current is real but negligible (the chip needs about ten times it). The drag uses the same rule. Checked on the rendered frames, the reader and every effect but the card's own hidden: frame-to-frame motion on the card is 0.0055 at a normal tap, 0 too far (7 cm) and with the reader off, 0.0001 with a weak reader, and a faint 0.0003 when badly tuned (12% of normal power); with the phone, 0.0048 at its normal tap and 0.0001 too far.
  - Into the chip (`power`, its wires and its glow): only once it is awake. The readout's chip power is the physics' own number (the power as a share of what the chip needs, (V / 2 V)²), not the gliding level, which read 99% for a full chip.

**Why it is built this way.** A timed film made you watch at its speed and couldn't respond to what you did. Stepping through the second half lets you look at each part for as long as you need. One readout in one place, and dimming everything else, means there is only ever one thing to read and one thing to look at. In the conversation you play the reader, because the most surprising thing about a passive card is that it never speaks first: nothing happens until the reader asks. The close-up has to make sense to someone who knows nothing about electronics, in about a minute. An earlier version was physically detailed (field lines with light gliding round them, a river of light along the whole power path, streaks through the card's coil, comets on both coils) but five things moved at once, in different directions, with the card lying right on the reader so the two coils overlapped, and the camera turning to a new angle at every step. Nobody could tell what was going on. The direction that matters is plain: up from the reader to the card is power and the question, down from the card to the reader is the answer. Electricity is drawn as beads of light, not as a glow on the copper, because copper is orange already: a glowing coil just looks like a coil. Everything runs on one clock, so the chip's wait and the bits keep their real proportions, and the picture follows the signal as a receiver's demodulator smooths it, so the gaps read as a soft rhythm instead of a strobe. The lights go down after the drop, because colour on a dark background is what makes the current and the rings glow. Every step was checked on screen against its sentence: an earlier version had steps you couldn't see (faint signal waves, a "chip works out its answer" step with nothing visible, a reader's chip off screen, and a power meter that said 100% before the chip had any power).

**What is simplified.**
- The rings are a picture of the field reaching from one coil to the other. In life the field doesn't travel between the coils at any speed you could see (it crosses the 3 cm in a tenth of a nanosecond), and it flips direction 13.56 million times a second. The rings' rise shows which way the power and the messages go.
- The current is drawn running one way round each coil, as in one half of each cycle; in life it flips 13.56 million times a second.
- The 3D follows the signal as a receiver's demodulator smooths it, with each dip drawn half again as deep, so a gap is a soft dip of about a tenth of a second rather than a 38 ms blink. The trace at the top shows the exact signal.
- In the answer, the card's switch changes the reader's field by a few percent. The blue rings swell, the reader's coil dips by 25%, and the trace draws each dip at 60%, so you can see it.
- The messages are slowed down about 16,000 times: at 106 kbit/s, the 45 bits of the answer take 0.44 ms.
- The distance is the drag's distance on the screen turned into centimetres, not a measurement. What happens at each distance is the physics engine's, as in the lab.
- The current runs into the chip along both of its wires. In a real chip, it is an alternating current through both, rectified inside the chip.
- The card's ID is made up, and its answer starts straight after the question; in a real tap the reader first sends REQA and gets ATQA back.
- The real-time stamps are round numbers inside a tap of about 5 ms. A full anticollision also selects the card (SELECT and SAK); the close-up stops at the ID.

**Likely questions.**
- Q: Why does the reader look like this? A: The brief was a modern, professional reader: one rounded slab rather than stacked boxes. The squircle outline and the round bevel are what make it read as one soft object.
- Q: Why does the card trail the pointer? A: A softer spring makes the card feel like it has weight, so it glides instead of sticking to the cursor. It is about a fifth of a second behind a moving pointer.
- Q: Why only one sentence at a time? A: Nobody can read two texts at once. The readout swaps its sentence, and the rest of the page fades out while it shows.
- Q: Why is the readout at the bottom? A: That is where people look for subtitles, and in the middle it is easy to find. An earlier version put it at the top left, beside the 3D, where it was hard to read. The small print under the sentence gives a little more for anyone who wants it, without making the sentence longer.
- Q: Why has the readout no box? A: A box is one more thing on screen. Small words straight on the background keep the eye on the card and the reader; the halo behind the letters is what keeps them readable where they cross the 3D. Without the box the readout is shorter, so every shot is framed a little larger, above it.
- Q: Where is the chip's processing? A: Two places: the card's chip flashes as it reads each byte and pulses while it works out its answer, and the reader's chip flashes as it reads the answer and glows while it checks it.
- Q: The drag already showed the current. Why does a drop start at step 1? A: The drag and the steps show different things. The drag shows how distance changes the power. The steps are the tap itself, slowed down, so they start at 0 ms with the reader's signal. An earlier version opened a drop on step 3, which skipped two steps and read as starting in the middle. A drop and a keyboard press now both start at step 1 (`confirmDrop` in `main.js`).
- Q: Are those real signals? A: Yes. The bytes are the exact frames of the first exchange in ISO/IEC 14443-3 anticollision, and the gaps, the load switching and the wait between them are placed exactly as ISO/IEC 14443-2 Type A does at 106 kbit/s, by the same code that runs the simulations further down the page. Only the speed is changed, and the ID is made up.
- Q: Are the lab's numbers real? A: Yes, as far as a model can be. They come from solving the card's and the reader's circuits with real coil sizes, turns, resistances and the chip's real wake-up voltage, calibrated so the card wakes exactly where the field falls to the standard's minimum, 1.5 A/m (about 4.9 cm). The same engine runs the simulations further down the page, and its tests check it.
- Q: Why does metal stop it? A: The field makes currents swirl in the metal (eddy currents), and they make a field of their own that cancels the reader's near the metal. It also changes the card's coil, which moves its tuning away from 13.56 MHz. That is why cards in a phone case with a metal plate, or next to keys, can fail.
- Q: Why does turning the card matter? A: Only the field that passes through the coil counts. Turned side-on, the field runs along the coil instead of through it, so almost none is collected (it goes with the cosine of the angle).
- Q: Why can't the visitor see the 13.56 MHz wave? A: It flips 13.56 million times a second. The lab shows what it does instead: how strong it is at the card, and how much voltage it makes there.
- Q: Why does it play by itself? A: So someone who has never seen it, or a presenter, can just watch it from start to finish. It stops the moment the visitor does anything, because then it's theirs to drive.
- Q: How does the field make electricity in the card's coil? A: The field flips direction 13.56 million times a second, so the amount of field passing through the card's coil keeps changing, and a changing field through a coil pushes a current round it (Faraday's law). That is step 3. The more field passes through, and the faster it changes, the more current.
- Q: Why do I have to press Ask? A: A passive card can't start a conversation: it has no power of its own and only answers when the reader asks. Making the visitor play the reader shows that.
- Q: What are the rings? A: The magnetic field, going from one coil to the other. Orange rings rise from the reader to the card: that field powers the card and carries the reader's question. Blue rings come down from the card: the answer. Each ring leaves in the shape of one coil and lands in the shape of the other, because the field goes through both.
- Q: Does the field really travel up like that? A: No. In life it reaches the card at once (a tenth of a nanosecond for 3 cm) and flips 13.56 million times a second. The rings are slowed right down to show which way the power and the messages go.
- Q: Why is the card held above the reader? A: So you can see the two coils apart, with the field crossing the gap. A real tap works up to about 4 cm, so 3 cm is realistic.
- Q: Why does the current go round every turn of the coil? A: Because that is where it flows: a coil is one long wire wound round and round, and the current goes through all of it. The more turns, the stronger the field the coil makes, and the more of the field it catches.
- Q: Why does the power go round the coils instead of straight from chip to chip? A: Because the chips never touch the field. Each chip only connects to its own coil, through a wire, and only the two coils are joined, through the field. So the path is chip, coil, field, coil, chip.
- Q: How can the card answer without a battery or a radio? A: It doesn't make waves of its own. It switches a load across its own coil, which changes how much of the reader's field it takes. The reader is still making the field, and feels its own coil change by a few percent. That is load modulation; in the close-up the blue rings swell and the reader's coil dips each time.
- Q: Why does the picture pulse softly when the real gaps are sharp? A: Because that is what a receiver sees. A card's demodulator smooths what its coil picks up before it decides on each bit; the picture follows that, so the gaps read as a rhythm instead of a strobe. The trace at the top shows the sharp signal itself.
- Q: Doesn't the chip lose power in each gap? A: The power does stop, but each gap is only 2.36 µs. The chip keeps running on the charge it has stored, so its power meter stays at 100%. The story's scene on stored energy shows what happens to a card that can't ride through.

### The story: a film played by scrolling (`js/story.js`, `js/landing.js`)
Owner: Mina Vian · 2026-11-21, updated 2026-11-21, then taken off the page's path 2026-11-24 · Issues #9, #19

**Off the page's path, for now.** The page explained the mechanism twice: here, with the key fob, and in the card close-up (What RFID is), with different objects, looks and controls, both opening with "The reader makes a magnetic field." For a two-minute demo that is one story too many, so the page now tells it once, with the card: the landing, the everyday taps, the card intro and its close-up (whose lab does what this story's lab did: distance, turning, metal), then Take it apart. `js/landing.js` removes this story's markup (`#story` and its `.track`) and never creates it or its lab (`STORY`) unless the address has `?story`, which brings everything below back exactly as it was. Without it, scrolling never plays the story, so the landing's objects stay where they are; the page is about a third shorter. Nothing here was deleted.

**What it does.** After the first screen, scrolling plays the first two minutes of `SCRIPT.md`. One plain sentence is on screen at a time, always top left, and a part is labelled only while the sentence names it:
- **Inside:** "They all use RFID." Then the objects turn to glass: "Inside each one: a coil and a chip." Each object gets `Coil` and `Chip` labels.
- **No battery:**
  - "The key has a battery." and "Pull it out.": the visitor drags the battery (or scrolling pulls it).
  - "The buttons stop working." and "The coil and chip don't need it."
  - The card comes back: "Your bank card has no battery at all." and "So what powers its chip?"
- **Power, Reply, Break it:** the lab (`js/lab.js`) runs these, and supplies the sentences that depend on what the visitor does.

The chapter bar at the bottom reads Intro, Inside, No battery, Power, Reply and Break it. On phones it shows the current chapter's name and a dot for each of the others.

**How it works.**
- **Progress in screens.** `landing.js` turns the scroll position into `scrollNow`, in screens (1 = one window height), and eases it toward the real scroll position, so a mouse wheel's steps feel like smooth playback. The count starts at the top of the empty `.track`, which comes after the everyday taps section, so the film begins once that section has scrolled away. The chapter buttons add the same offset.
- **One timeline.** `story.js` holds the timing (`TIME`), and `timeline(s)` turns `s` into progress values for the 3D. The sentences that depend only on the scroll are a list of ranges (`SAY`, and `AFTER` for after the battery is out). `sentence()` picks the one for the moment. In the lab scenes, it takes the lab's sentence instead. `speak()` swaps the text and replays a short fade-in.
- **Labels** (`CALLOUTS`) each name the sentences that show them (`when`). They fade in and out with the sentence, and each sits outside its object, joined to its part by a thin line.
- **The battery handle** is a real button over the battery. Dragging it more than 22 mm (in the key's own size) frees the battery; Enter, Space or an arrow key does the same.
- **One design frame.** The whole film is laid out on a 1440 × 900 frame (390 × 844 on phones), scaled by one factor to fit the window and centred (`designFrame` in `landing.js`). It sets `--u` (one design pixel), `--fx` and `--fy` for the CSS, and every size and place in the film comes from them. So every screen of the same shape shows exactly the same picture, only bigger or smaller.

**Why it is built this way.** The visitors are ordinary people. One short sentence at a time, beside the thing it names, is quicker to read than a list. The brief rejects videos, so the visitor drives it: the first hands-on moment (pulling the battery) comes at about 0:20.

**How to check it.** Serve the folder, open it and scroll. With `?debug`, `__hero.state.scroll` shows the progress. Resize the window: the picture keeps its layout.

**Likely questions.**

- Q: What if someone doesn't scroll or drag? A: A "Scroll" cue sits under the first screen, and scrolling alone pulls the battery out and brings the key to the reader.

### The simulation: physics, protocol and reader (`js/rfid/`)
Owner: Mina Vian · 2026-11-21 · Issue #19

**What it does.** Everything the site shows reacting is computed here, from the visitor's inputs, in real units. Seven small files, each with one job:

| File | Job |
|---|---|
| `physics.js` | The coils: the field, the voltage at the chip, whether it wakes, and the size of its answer |
| `iso14443a.js` | The card standard both sides share: frames, check bits, CRC_A, and how bits become pauses and flickers |
| `lf.js` | The car key's 125 kHz message (the EM4100 format: a header, the ID, row and column check bits) |
| `tag.js` | The chips: the card's chip with the standard's states, and the key's chip |
| `air.js` | Turns pauses and switch patterns into the samples a reader measures, with noise |
| `reader.js` | The receiver: reads IDs from samples alone, and runs a whole conversation with a card |
| `channel.js` | Joins a reader to the cards in its field, and records every exchange for drawing |

**How it works.**
- **Physics** (`physics.js`, `solve`). The reader's coil and the tag's coil are treated as coaxial circular loops of the real parts' sizes (as circles of the same area). Their link is the mutual inductance from Maxwell's formula with elliptic integrals (`loopMutual`, `ellipticKE`), times the cosine of the angle between them. The voltage induced in the tag's coil is V = ω·M·I (Faraday's law). The tag is a tuned circuit: the coil (inductance from its size and turns, `coilInductance`) in series with the capacitor and the chip, solved with complex numbers. The chip is modelled as a resistor. Above its limit (3.3 V for the card) it soaks up the extra, which looks like a smaller resistor; `solve` finds that resistor by bisection.
- **Calibration** (runs once). The card's chip load is set so it wakes exactly where the pad's field falls to 1.5 A/m, the standard's minimum (ISO/IEC 14443-2); that puts the pad's range at 4.85 cm. The pad's current is set so its field at the centre is 7.5 A/m, the standard's maximum. The car's reader is set so the key wakes up to 4 cm away. The card's chip ends up drawing about 5 mW and the key's about 75 µW, both realistic.
- **The answer.** When the chip closes its switch, it changes the impedance the tag reflects into the reader's coil, (ωM)²/Z, and the reader's current changes by the fraction `dip`. That dip is the answer.
- **Metal** is a perfect conductor, handled with mirror images: a second reader coil behind the plate, mirrored, with the current reversed (cutting the field at the tag), and a mirror of the tag's own coil (lowering its inductance, so its tuning rises).
- **The card standard** (`iso14443a.js`). Reader to card: each bit is placed as a pause by modified Miller coding (`millerPauses`), and the card decodes the pauses back (`millerDecode`). Card to reader: Manchester coding on an 847.5 kHz subcarrier (`manchesterSwitch`): flicker in the first half of a bit is a 1, in the second half a 0. Every byte carries an odd parity bit; the longer messages carry CRC_A. The card waits the standard's delay before answering (`answerDelay`).
- **The chips** (`tag.js`). The card's chip only ever gets the bits it decoded from pauses in the field, and only answers by choosing bits for its switch. It follows the standard's states (IDLE, READY, ACTIVE, HALT): it answers "Anyone there?" with ATQA, its ID during anticollision (only if its ID starts with the bits the reader names), and SAK when selected. A card with random IDs makes up a new one, starting with 08, each time it powers up.
- **The reader** (`reader.js`) gets nothing but samples. `hearCard` measures the noise in the quiet stretch before a card may answer, then slides a 16-sample window along, correlating it with a sine and cosine at 847.5 kHz to measure the flicker. It finds the start of the answer, then reads each bit by comparing its two halves; flicker in both halves, about equally, is a clash between two cards. `activate` runs the whole conversation: REQA, then anticollision (narrowing down at each clash by choosing a side), then SELECT, with every check bit and check number tested. `hearKey` tries every alignment of the key's message until one passes all its checks.
- **The channel** (`channel.js`) is the only file that knows both sides. It renders each exchange, lets each powered card hear and answer, and adds each card's dip to the reader's samples. A card whose storage capacitor can't carry it through a pause resets instead of answering.

**Why it is built this way.** The brief says outputs must be computed from inputs, and the organisers' own example falls short because its receiver could peek at the sender's data. Here the reader is a separate file that only gets samples, and a test checks that it never refers to the tag, the channel or the physics. Every file works both as a plain browser script and in Node, so the same code runs on the site and in the tests.

**How to check it.** Run `node --test` in the project's folder or open `tests/` in the browser. In the console, `RFID.physics.solve({ tag: 'card', distance: .03 })` returns the numbers for a card 3 cm from the pad.

**Likely questions.**
- Q: Why model the chip as a resistor? A: To the coil, a running chip is a load drawing power. A resistor is the simplest honest model of that. The limiter makes it a smaller resistor when there is extra power, as a real chip's shunt regulator does.
- Q: Is the car key's protocol real? A: The key speaks the EM4100 format, a real and common 125 kHz read-only format. Real car keys differ by maker and many add a secret handshake on top; the scene only needs the part they share: a battery-free chip answering through the field.
- Q: What is simplified? A: The coils are treated as circles of the same area; the reader holds its current steady; metal is a perfect conductor; noise is plain random noise. The tests check the parts that are exact: the standard's own CRC examples, the coding, and that 1.5 A/m wakes the card.

### The lab: Power, Reply, Break it (`js/lab.js`)
Owner: Mina Vian · 2026-11-21, updated 2026-11-21 · Issue #19

**What it does.** The reader and the key, live, in three scenes.
- **Power.** The visitor brings the key to the reader (scrolling also lowers it). Field lines rise from the reader's coil, copper sparks run round the key's coil, and a power bar fills toward its wake-up line. The sentences step forward one at a time:
  1. "Move the key to the reader."
  2. "The reader makes a magnetic field."
  3. "The field makes electricity in the coil."
  4. "Enough power wakes the chip."
  5. "The reader is the battery."
- **Reply.** "Now the chip replies." "It has no radio." "It takes more power, then less." With each change, the key's coil glows brighter or dimmer. A trace under the reader, labelled "What the reader feels", dips with each change. The ID display fills in `3F 9A 12 C7`, decoded from those dips: "That's the 'ID' in RFID."
- **Break it.** Three buttons (Turn it, Add metal, Use a card) and the drag. The sentence says what broke ("Too far. Not enough power.", "Turned. The field misses the coil.", "Metal pushes the field away.") and asks for the next way to break it. Then: "That's why you tap close and flat." After 4 idle seconds, a ghost hand lifts the key once.

**How it works.**
- **Every frame**, `update` calls `physics.solve` with the key's distance (plus about a millimetre of hand drift), angle and metal.
- **The power sentences** come from the physics: out of reach, field only, electricity, awake. They only move forward one step at a time, and each stays at least 1.5 s, so a fast scroll can't skip one.
- **The key's reply** is made one bit at a time, slowed to 70 ms per bit (really 512 µs). The reader decides each bit from those samples. When a whole message has passed, `reader.hearKey` checks it from the samples alone before the display turns green. At the "spell" moment the reader starts listening afresh, from the end of one message into the next one's header.
- **The card** replies only when asked: each time it wakes, a whole conversation runs through `channel` and `reader.activate`, and the trace plays the samples back.
- **What broke** (`reasonFor`) is the one change that would fix the read: metal first, then the turn, then the distance.
- **Timings people see** (how long a sentence stays, idle time) use real seconds. The simulation uses the frame clock.
- **Sizes** come from the design frame (`geo.u`), like the rest of the film.
- **The reader pad is drawn at the true size of the reader in use** (`padScale`): a small start-button reader (a 1.6 cm coil) for the key, and a payment terminal (a 3.5 cm coil) for the card. Its copper ring always matches the coil the field lines come from. The camera zooms in close on the key (8000 design pixels per meter) and eases out for the card (5600), so the tag always fills the view.

**Why it is built this way.** The first hands-on part should teach by doing. Each sentence only appears when the thing it says is really happening in the simulation.

**How to check it.** Scroll to Power and drag the key. With `?debug`, `__lab.bits` shows the bits the reader decided, and `__lab.fastForward(70)` plays 70 bits at once.

**Likely questions.**
- Q: Is the ID really decoded? A: Yes. The display only shows what the reader read from the samples, and turns green only when the message passes its checks.
- Q: Why 2.5 cm when scrolling? A: Close enough to read, and close enough to the edge that metal or a turn breaks it, so every lesson is one click away.

### Publishing the site (`.github/workflows/pages.yml`, `hosting/`)
Owner: Mina Vian · 2026-11-24 · Issue #33

**What it does.** Puts the site online at https://hackathon.minavian.com/ccavc/RFIDtechnology/, the public link the judges open. Every merge into `main` goes live by itself in about a minute. Nobody uploads anything by hand.

**How it works.**
- `.github/workflows/pages.yml` runs on GitHub's servers each time `main` changes (or from the Actions tab, "Run workflow").
- It copies every file Git tracks into `_site/ccavc/RFIDtechnology/`, except the dot-folders (`.github`, `.claude`), the notes (`*.md`) and `hosting/`. The site needs no build, so the files go up as they are.
- It adds the domain's own two pages from `hosting/` to the top of `_site`:
  - `index.html` sends the bare domain to the site, keeping anything after the address (so `hackathon.minavian.com/?play` starts presenter mode).
  - `404.html` is what GitHub Pages shows for an address it has no file for. Addresses are case-sensitive there, so it sends `/ccavc`, `/ccavc/` and any other spelling of `/ccavc/rfidtechnology/…` to the exact one. Anything else says "Nothing here." with a link to the site.
- It always publishes the newest `main` (`ref: main` on the checkout), not the commit that started the run. On 2026-11-24, GitHub started one commit's run late, after two newer ones, and it put the older code back on the site. Now the last run to finish still publishes the latest code.
- It runs in two jobs: `build` copies the files and uploads them, then `deploy` hands them to GitHub Pages. `deploy` waits for `build` to finish (`needs: build`). If a deploy try fails, it waits and tries again, up to three times (`first`, `second`, `third`), so nobody has to press "Re-run".
- GitHub Pages publishes `_site`. The repo's Pages settings give it the custom domain `hackathon.minavian.com`.
- Visitors reach it through Cloudflare, like the team's other sites. The DNS record `CNAME hackathon → minavian.github.io` is set to **Proxied**, and the zone's SSL mode is **Full**, so Cloudflare talks to GitHub over HTTPS. Visitors get Cloudflare's certificate for `*.minavian.com`, which renews by itself and has a backup.
- **Changes show at once.** Two Cloudflare rules apply to `hackathon.minavian.com` only. A Cache Rule, "hackathon: always fresh from GitHub", stops Cloudflare keeping copies. A Response Header Transform Rule, "hackathon: browsers check for the newest version", sends `Cache-Control: no-cache`. So a browser asks for every file on every visit. An unchanged file costs only a short "304 Not Modified" answer, with no download, because GitHub sends an ETag (a fingerprint of the file). Without the rules, GitHub's `max-age=600` let browsers keep old files for up to 10 minutes after a merge.

**Why it is built this way.** The site is plain files that run from any folder, because every path in it is relative (`js/lab.js`, never `/js/lab.js`). So it can sit two folders deep with no changes. GitHub Pages is free for a public repo, needs no keys or passwords in the repo, and the publish runs in the open where judges can see it. The folder `ccavc/RFIDtechnology/` leaves room for other hackathon projects on the same domain later. We looked at publishing to Cloudflare Pages (where minavian.com lives), but that needs a Cloudflare key stored in GitHub, or Cloudflare's app on the GitHub account. Instead, Cloudflare only sits in front of GitHub Pages.

**How to check it.** Open the live link: the page should look the same as when you serve the folder yourself. In the repo, the Actions tab shows a green "Publish the site" run for each merge. To try the copy step locally, run the workflow's commands, then serve `_site` (`python -m http.server --directory _site`) and open the root. You should land on `/ccavc/RFIDtechnology/`.

**Likely questions.**
- Q: Why are the Markdown notes left out? A: They are for the team. They stay readable in the public repo, but the site doesn't need them.
- Q: What if GitHub is down? A: The site is down too, and the same goes for Cloudflare. Any static host would work as a backup, because there is no server code.
- Q: Why run it through Cloudflare at all? A: The same set-up as the team's other sites, one certificate that renews itself with a backup, and the two rules that make every change show at once. Before it, a visitor during the 15 minutes before GitHub's certificate existed got a certificate warning, and their browser remembered that.
- Q: Why two jobs, not one? A: With upload and deploy in one job, the deploy step sometimes asked for the files a moment before GitHub had registered them, and failed with "No artifacts named github-pages".
